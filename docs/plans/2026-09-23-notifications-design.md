# 站内消息与可扩展投递

用户确认先实施站内消息和未读数，后续扩展飞书、钉钉等渠道。本期通知触发：创建任务时分配执行人、执行人变更、他人在执行人的任务下发表评论。自分配任务也提醒本人，自评论不提醒；不补发历史事件。到期、验收、@ 提及留待后续定义规则。

## 数据与一致性

- notification_events：不可变的业务通知事件，类型、版本、关联项目/任务/评论、操作者、操作幂等键及最小展示快照。网页与 MCP 共用事件生成入口。
- notifications：事件收件人与站内已读状态。每个事件每个收件人唯一。
- notification_deliveries：每条通知、渠道、目标的投递记录，保存状态、重试次数、下次执行时间、租约与错误。站内渠道在事务内立即投递；未来外部渠道只写 pending 记录，由后台 worker 调用适配器，不能在任务事务里访问外网。凭证属于渠道配置，不放入事件或错误文本。

三者与任务变更处于同一数据库事务：操作回滚不产生提醒，操作重试不重复通知。站内已读与外部送达独立，后续无需改变业务事件与收件人表即可扩展渠道策略、配置、worker、退避与死信处理。外部网络通常只能保证至少一次投递；未来适配器应尽量传幂等键，不宣称跨平台恰好一次。

## 权限与产品行为

仅收件人能读取或标记自己的消息，包括管理员也不能读取其他人的收件箱。查询与未读数均重新检查项目成员身份、项目/任务删除状态，评论删除后对应通知不再展示；归档项目仍可查看历史提醒。不保存评论正文。旧提醒采用事件发生时的任务标题，点击进入当前任务。

全局铃铛显示未读数（99+ 上限）：桌面端位于内容区右上角，窄屏位于品牌栏右侧。点击弹层只展示未读消息，每次加载 20 条并可滚动加载后续消息；点击消息即标为已读、从弹层移除并打开任务详情。支持全部标为已读，不提供独立消息页和手动刷新。阅读不修改任务状态。全部已读使用服务器返回的时间边界，避免把之后新产生的通知批量读掉；服务端保留已读记录，便于后续渠道扩展。

前台每 15 秒查询未读数；弹层打开时同步刷新未读列表。隐藏页面暂停，切回页面、网络恢复或主动操作后立即刷新，清理请求与定时器。其他页面不刷新业务列表。服务器持续存储离线期间通知，下次登录可见。
