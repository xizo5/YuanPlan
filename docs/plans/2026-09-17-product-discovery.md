# 项目管理软件：需求讨论记录

状态：核心方向已确认，详细设计与开发任务已进入整理。此文档保留讨论决策，具体建议默认值见同目录 design 文档，不代表所有细节均已获用户确认。

## 已确认决策

- 独立开发，参考 Kaneo 的简洁体验和核心任务管理功能；不基于 Kaneo 或 Plane 源码 fork 开发。
- 使用自己的产品设计与实现，正常复用符合许可要求的开源框架和组件。
- 计划长期开放源代码，可接受 AGPL 的源码提供义务；本项目具体许可证尚未选定。
- 保留后续公开发布及商业销售的可能。
- 主技术栈已确认：前端 React + Vite + TypeScript，后端 Node.js + Hono，数据库 PostgreSQL，数据访问与迁移使用 Drizzle，富文本使用 Tiptap 开源编辑器及开源扩展。
- 架构采用模块化单体，网页 API 与 MCP 复用同一业务、权限和审计逻辑；首版 Docker Compose 部署为一个应用容器与 PostgreSQL，附件保存在持久化目录并经权限校验访问。
- 首版不引入独立 Redis、消息队列或搜索服务；备份同时覆盖数据库与附件。
- 前端必须采用统一、可靠的成熟 UI 组件库，复用现成基础组件；布局与交互参考 Kaneo、Plane，独立实现设计与代码。
- UI 采用 Mantine 作为唯一通用组件库，使用统一主题和复用业务组件；具体约束见 `2026-09-17-ui-direction.md`。
- 目标是轻量团队应用：部署简单、操作流畅、代码容易维护。不追求极限低内存；2 核、2GB 左右环境作为候选验证环境，容量与资源指标待定义和实测。
- 用户登录后可以创建、管理项目。
- 保留简化的项目成员机制；团队可选，用于组织和选择人员。
- 项目拥有独立成员名单；从团队选择成员加入项目，不自动让整个团队获得访问权限。
- 项目角色固定为管理员、成员、只读。三种角色均可查看任务、Wiki、附件和操作记录；管理员和成员可创建、编辑任务与 Wiki、分配执行人、调整状态、上传附件和发表评论；仅管理员可删除任务或 Wiki、管理成员及角色、修改项目设置、归档或删除项目。
- 成员可编辑项目内所有任务和文档，不受创建者或执行人身份限制；项目创建者自动成为管理员，每个项目至少保留一名管理员。
- 团队身份不自动授予项目权限；MCP 遵守调用者的项目权限。
- 首版不增加工作空间层级；用户登录后直接创建项目，可直接邀请项目成员，也可从可选团队中选择参与者。
- 项目可关联团队，但关联本身不授予访问权限，项目成员名单独立保存。
- 团队管理员管理团队名单，项目管理员管理项目成员，两种身份不自动继承权限；团队新增成员不会自动加入已有项目。
- 从团队移除人员时，向有权限的管理员提示其仍参与的项目，由管理员决定是否同时移除项目成员；不得泄露其无权查看的项目。
- 删除团队不删除关联项目，项目成员关系继续保留；相关联信息需要解除。
- 主导航采用我的项目、我的任务、团队等简洁入口；个人使用无需先配置组织结构。
- 首版使用邮箱和密码登录，暂不加入第三方登录。
- 注册支持仅邀请与开放注册两种模式，默认仅邀请；开放注册不授予任何已有项目的访问权限。
- 项目管理员填写受邀邮箱并选择角色，生成绑定邮箱的邀请链接；链接可过期、可撤销、使用后失效。受邀者使用匹配账号登录，未注册者先注册再接受邀请。
- 邮件服务可选；未配置时管理员可以复制邀请链接自行发送。团队邀请与项目邀请分别管理，不自动互授权限。
- 安装初始化创建系统管理员，负责注册设置、邮件配置和账号管理；系统管理员与项目管理员分离，项目内容访问仍按项目权限判断。
- 账号恢复需覆盖邮件找回及未配置邮件时的恢复场景，具体身份验证和恢复流程待细化。
- 项目内任务、Wiki 和附件继承项目权限，MCP 使用相同权限规则。
- 项目内包含轻量 Wiki 文档模块。
- 提供 MCP 接口，便于大模型及 AI Agent 访问业务能力。
- 看板采用固定四列：待办、进行中、待验收、已完成。各项目统一使用，不提供列的新增、删除、改名或排序配置。
- 不采用此前讨论的自定义列及状态类别配置方案。
- 固定四个状态之间允许自由流转，可以跳过中间阶段，也可以将已完成任务退回进行中等状态。
- 待验收仅表达任务阶段，首版不设置强制审批或指定审批人。
- 每个项目提供任务和文档入口，文档继承项目成员权限。
- Wiki 使用轻量富文本编辑器，支持标题、列表、图片、表格、代码块及常见 Markdown 输入快捷方式。
- Wiki 首版提供页面目录、自动保存、历史版本和任务链接；多人编辑同一文档时提示版本冲突，暂不做实时共同编辑。
- MCP 文档能力采用 Markdown 读写方向，具体工具、支持格式、转换规则和写入权限待细化。
- MCP 首版支持查询可访问项目、项目详情和成员；搜索、读取、创建与编辑任务及子任务，分配执行人、修改状态，读取和发表评论，搜索、读取、创建与更新 Wiki，查询任务变更记录及文档版本。
- MCP 首版不提供项目、任务或文档删除，也不提供成员和权限管理；上述管理操作在网页内完成。
- MCP 凭据按用户创建，可限定指定项目、只读或读写范围及有效期，支持随时撤销。实际授权为用户当前项目权限与凭据授权范围的交集；移除项目成员后其凭据立即失去该项目访问权。
- MCP 修改记录授权账号、凭据标识与 MCP 来源，不记录凭据明文；更新既有任务或文档时检查版本，冲突时返回失败，不覆盖较新的内容。
- 每个任务最多一个负责人（执行人），允许未分配；从项目成员中选择，不支持多负责人。
- 创建者与执行人是独立概念：创建者记录任务由谁创建，不随任务转交而改变；执行人可以更换。
- 用户已撤回“创建者自动负责、只有负责人才能修改”的提议，恢复原单负责人方案。任务编辑权限按项目角色另行细化，不增加仅执行人可修改的限制。
- 首版支持一层子任务，不允许子任务继续嵌套；每个子任务具有独立执行人和固定四态中的当前状态。
- 父任务显示子任务完成进度，父任务状态手动调整，不随子任务完成情况自动流转。
- 任务创建仅标题必填；描述支持富文本且可选，状态默认待办，执行人可选且为单人。
- 任务优先级为低、普通、高、紧急，默认普通；标签可多选，开始日期、截止日期和附件均可选。
- 系统自动记录任务编号、创建者、创建时间和更新时间；任务详情提供评论和操作记录，用于追踪状态、执行人等变化。
- 子任务沿用相同基础字段。
- 任务和 Wiki 每次成功保存都必须留下可追溯记录，能够定位每次变动对应的操作人；包括自动保存和通过 MCP 发起的保存。审计与版本机制属于首版必要能力。
- 历史记录默认长期保留，不自动清理；存储优化不得丢失各次成功保存的记录或版本可恢复性。后续可讨论归档策略。
- 已确认变更追溯规则：区分创建者、执行人与实际修改人；任务记录修改前后的字段值，Wiki 保留内容版本与差异；自动保存逐次留痕，连续编辑可在界面聚合但底层记录保留。
- 恢复旧版本产生新版本与恢复操作记录，不覆盖原历史；删除记录操作人和时间，采用软删除方向，具体永久删除策略待定。
- 操作历史不能通过产品界面或普通 API 编辑、删除，项目管理员也不例外；账号停用后仍保留历史身份关联。
- 业务保存与审计记录须原子提交。MCP 修改绑定认证身份并记录来源；共享凭据只能追溯到账号，不能区分背后实际操作者。

## 变更追溯实现约束与待细化事项

- 每次成功保存生成独立记录，业务保存与审计写入在同一数据库事务中完成；审计失败则该次保存失败。
- 记录资源与版本标识、操作人稳定 ID、操作时的显示名、服务端时间、操作类型、来源和变更字段；文本内容保留可恢复的版本或可靠差异链。仅保存最后修改人不满足要求。
- 区分创建者、执行人和实际修改人。保存者始终作为本次修改人，转交任务不会改变历史归属。
- 自动保存按实际成功写入记录，不按每次按键记录；界面可聚合同一人的连续修改，但保留底层各次记录。
- MCP 凭据绑定具体用户或独立服务账号；记录授权身份与 MCP 来源，可额外记录客户端标识，但客户端标识不作为可信的人类身份依据。共享凭据无法区分实际操作者。
- 版本恢复新增一个版本及操作记录，不覆盖旧历史；失败或版本冲突的写入不标记为成功修改，必要时另记失败事件。
- 删除和恢复记录操作人，首版倾向软删除；账号停用后保留历史身份关联。永久删除、个人信息处理及保留期限需另定。
- 历史记录在产品界面和普通 API 中只读，项目管理员也不能编辑或删除；这不等于能够阻止拥有数据库或服务器权限的人篡改。

## 首版范围建议（尚未逐项确认）

- 基础任务管理：列表、看板、负责人、优先级、标签、日期、评论、附件和基础筛选。
- Wiki：基础搜索，以及目录层级、任务关联和版本恢复的具体规则待细化。
- MCP：已确认业务范围，工具契约、传输方式及 Markdown 转换细节待定义。
- 备份恢复与升级迁移的具体交付流程和验收指标待细化。
- 暂缓复杂工作流、企业 SSO、复杂组织权限、多人实时协同编辑和大量第三方集成。

## 待讨论问题

1. 任务取消、归档和删除的处理；重新打开已完成任务可通过状态回退实现。
2. 邀请有效期、邮箱身份验证、账号恢复、系统管理员与项目角色管理细节。
3. 子任务在列表和看板中的展示、归档和删除规则。
4. Wiki 目录层级、版本保存与恢复规则、搜索、任务关联及 Markdown 转换范围。
5. MCP 工具契约、传输方式与凭据实现；审计覆盖范围、版本存储方式及长期历史归档方案。
6. UI 主题细节、依赖兼容版本、附件限制、部署与备份恢复细节。
7. 性能和容量目标、首版验收范围、迭代优先级。
8. 开源许可证、品牌及第三方许可声明。
