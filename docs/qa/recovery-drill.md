# 部署与恢复演练记录

日期：2026-09-20。范围：T33 实现验证、T34 部分演练。环境：Windows 宿主机、Docker Engine 28.1.1/Linux 容器、Node 22、PostgreSQL 17。

## 设计与边界

沿用 V1 单应用加 PostgreSQL 架构。迁移角色拥有表，应用角色只获得业务所需权限；备份使用维护模式、数据库导出快照和既有附件锁，不改变业务历史保留策略。恢复只面向空数据库与空附件目录，拒绝原地覆盖。数据库与文件系统无法共用事务，因此失败留下标记和现场，由运维重新准备空目标。

## 自动化数据库验证

执行 `npm test`：6 个文件、65 项测试通过；`npm run typecheck` 与 `npm run build` 通过。

新增 `tests/backup-restore.test.ts` 使用临时独立 PostgreSQL 数据库和 `.data` 下的临时附件目录。测试账号需要 CREATEDB 权限；PATH 需要 `pg_dump` 和 `pg_restore`。新数据库名固定为随机 `yp_restore_*_test`，清理仅针对本轮记录的数据库和目录。

| 场景 | 结果 |
| --- | --- |
| 非维护模式备份、重复输出目录、非空恢复目标 | 拒绝 |
| 用户、项目、任务、Wiki、版本、审计、邀请、凭据与权限恢复 | 所有业务表逐行比较一致 |
| 已从当前资源移除的历史附件 | 内容及 SHA-256 一致，仍纳入备份 |
| 未登记孤立文件 | 不纳入备份 |
| 错误密钥、损坏附件、损坏数据库归档 | 恢复前拒绝 |
| 上传共享维护锁与备份独占锁 | 观察 PostgreSQL 锁等待，释放后完成 |
| pg_dump 程序启动失败 | 不产生有效清单，维护保持开启 |
| 健康检查、认证/公共/MCP API 的维护行为 | 健康 200，其余 503 并含 Retry-After |

## 容器演练

构建 `yuanplan:local` 成功。在 `yuanplan-verify-t33` 项目中从空数据卷启动数据库、迁移与应用。迁移退出 0；应用健康、静态资源 200，进程 UID 非 0。数据库实际检查确认运行角色为 `yuanplan_app`，无 public CREATE、审计 UPDATE 和版本 DELETE 权限。

创建临时用户数据，开启维护并通过镜像内 CLI 生成备份（4 个迁移，0 个附件）。导出后，在独立的 `yuanplan-restore-t33` 项目及全新数据库/附件卷内恢复成功。重新运行迁移授权后，测试用户保留，审计 DELETE 权限仍被拒绝；维护时业务接口 503，关闭维护后返回 200。强制重建应用容器后再次确认用户数据保留。容器演练从首次启动到恢复与重建检查约 3 分钟，属于功能演练，不代表容量或恢复时间目标。

一次检查在容器刚启动时遇到连接拒绝；待服务就绪后复验通过。部署指南明确要求等待健康检查，而非把 `up -d` 返回作为服务就绪依据。

容器演练仅含少量用户数据；带附件、完整历史及权限的逐项恢复由上述数据库测试覆盖。两个容器项目位于同一 Docker 主机，不能标记为真正异机恢复完成。临时容器、网络及命名卷在演练后清理，开发数据库不参与恢复或清理。
